BMAD para Devs

Fluxo de desenvolvimento com o Developer Agent (Amelia) — do sprint planning ao code review, usando os triggers certos para cada situação.
Developer Agent Dev Loop Quick Dev Brownfield project-context.md
00O papel humano nesta fase

O Developer Agent (Amelia) é poderoso, mas a qualidade do código gerado depende diretamente da qualidade do que você coloca como contexto. Amelia não sabe o que não está documentado — não conhece a dívida técnica tácita, as restrições de ambiente não escritas ou as decisões tomadas em reunião que nunca viraram artefato.

O papel do desenvolvedor humano com o BMAD não é digitar código — é ser o guardião da qualidade e do contexto. Você decide o que entra como input, revisa o que sai como output e identifica quando o agente tomou uma decisão que parece certa mas conflita com algo que só você sabe.

🧠
Você traz
Contexto não documentado, restrições de ambiente, julgamento sobre tradeoffs, conhecimento da dívida técnica e validação do output gerado
⚡
Amelia traz
Velocidade de implementação, consistência com a arquitetura definida, cobertura de critérios de aceite e revisão sistemática do próprio código
Princípio central: o Dev Loop do BMAD não é "peça e aceite". É "peça, revise, corrija e aprove". O agente reduz esforço mecânico — a responsabilidade técnica continua sendo sua.
01O Developer Agent (Amelia)

O Developer Agent é o agente central do fluxo de execução no BMAD. Diferente dos agentes de planejamento (PM, Architect), ele opera dentro do ciclo de implementação e é o único que tem acesso direto ao código. Seu skill ID é bmad-agent-dev.

Um detalhe importante: na v6 do BMAD, a geração de testes E2E também é roteada através do Developer Agent — não existe um agente QA separado no módulo base BMM. O Test Architect completo (TEA) vive em um módulo separado.

⚡
Implementação
Executa stories com alinhamento à arquitetura e ao contexto do projeto
🔍
Code Review
Revisa o próprio output contra os critérios de aceite da story
🧪
QA / Testes
Gera suites de testes E2E detectando o framework usado no projeto
📋
Sprint Planning
Prioriza e organiza stories para o sprint com base no contexto técnico
02Todos os triggers

O Developer Agent tem 7 triggers. Todos são workflow triggers — você digita o código e o agente inicia o workflow estruturado, pedindo inputs em cada etapa.

Trigger Nome O que faz
DS Dev Story Implementa uma story completa usando o contexto do projeto e os critérios de aceite definidos
QD Quick Dev Desenvolvimento rápido com menos supervisão — comprime intenção, roteia para o menor caminho seguro e executa
QA QA Test Generation Gera suite de testes E2E analisando codebase e detectando o framework (Jest, Vitest, Playwright, Cypress)
CR Code Review Revisa o código implementado contra os critérios de aceite da story e os padrões do projeto
SP Sprint Planning Prioriza e ordena stories do sprint com base em dependências e contexto técnico
CS Create Story Cria uma story tecnicamente detalhada, com contexto de implementação e critérios testáveis
ER Epic Retrospective Consolida aprendizados técnicos do epic concluído e sugere melhorias para o próximo ciclo
03Dev Story (DS) — para stories já definidas

É o trigger central do fluxo. Use quando você já tem uma story estruturada — gerada pelo PM via CE, pelo Developer via CS, ou escrita manualmente. O agente lê a story, carrega o project-context.md, alinha com a arquitetura e implementa.

O que o agente carrega automaticamente
  • Conteúdo da story (critérios de aceite, contexto técnico)
  • project-context.md — stack, convenções e regras críticas
  • Documentos de arquitetura relevantes
  • Padrões de código definidos para o projeto
Regra importante: não pule camadas

Se durante a implementação você perceber que precisa mudar algo na arquitetura, não peça ao Developer para fazer isso. Volte ao Architect (bmad-architect), atualize o documento de arquitetura, e então retome com o Developer. Pular essa etapa gera inconsistência entre código e arquitetura que se acumula ao longo do tempo.

04Quick Dev (QD) — para tarefas sem story formal

O Quick Dev existe para reduzir o atrito de supervisão humana sem abrir mão dos checkpoints de qualidade. É o caminho certo para bugs, ajustes pontuais, refatorações pequenas e tarefas que caberiam em uma página de notas.

Regra prática: se você ficaria desconfortável pulando PRD e documento de arquitetura, use o fluxo completo com DS. Se a mudança cabe em uma página de notas, use QD.

→

A entrada pode ser qualquer coisa: frases brutas, link de bug tracker, output do plan mode, texto de um chat ou número de uma story do epics.md. O agente comprime essa intenção em um objetivo coerente antes de executar.

✅ Bom para QD
  • Correção de bug específico
  • Ajuste de estilo ou layout
  • Refatoração de um arquivo
  • Adicionar validação a um campo
  • Correção de typo em texto
❌ Não use QD para
  • Novas funcionalidades complexas
  • Mudanças que afetam múltiplos módulos
  • Alterações em banco de dados
  • Qualquer coisa que precise de PRD
05Quick Dev — como o design funciona por dentro

O QD tem 5 princípios de design que explicam por que ele funciona bem quando bem usado:

1
Comprimir intenção primeiro — antes de executar de forma autônoma, transforma o pedido em um objetivo coerente e sem contradições. Intervenção humana acontece aqui.
2
Rotear para o menor caminho seguro — mudanças de zero impacto colateral vão direto para implementação. Tudo que tem risco passa por planejamento antes.
3
Rodar mais tempo com menos supervisão — após o spec aprovado, o agente executa com o spec como limite, sem checkpoints constantes no meio do caminho.
4
Diagnosticar falha na camada certa — se o código está errado porque a intenção estava errada, consertar o código é o conserto errado. O workflow identifica a camada da falha e regenera a partir dali.
5
Revisão como triagem, não auditoria — achados incidentais (não causalmente ligados à mudança atual) são adiados. O sistema otimiza para qualidade de sinal, não para recall exaustivo.
06project-context.md — a fundação do Dev Loop

O project-context.md é o arquivo que garante que todos os agentes sigam as mesmas convenções em todos os workflows. É o equivalente ao claude.md, mas estruturado especificamente para regras de implementação.

Adicione ao seu AGENTS.md: Important project context and conventions are located in _bmad-output/project-context.md
Como criar

Três opções, dependendo do seu momento:

  • Manual — quando você já sabe as regras que quer documentar
  • Após arquitetura — rode bmad-generate-project-context para capturar as decisões tomadas
  • Projeto existente — rode bmad-generate-project-context para que o workflow analise o codebase e identifique os padrões

project_name: 'MeuProjeto'

## Technology Stack & Versions
- Node.js 20.x, TypeScript 5.3, React 18.2
- State: Zustand | Testing: Vitest, Playwright
- Styling: Tailwind CSS

## Critical Implementation Rules
**TypeScript:** Strict mode, sem `any`, use `interface` para APIs públicas
**Code Organization:**
  - Componentes em `/src/components/` com testes co-localizados
  - API calls usam o singleton `apiClient` — nunca usar fetch diretamente

## Do NOT do (anti-patterns)
- Nunca mutar estado diretamente — use os setters do Zustand
- Nunca adicionar lógica de negócio em componentes React

Use o project-context.md quando perceber que agentes tomam decisões inconsistentes entre stories — é o sinal de que o contexto está fragmentado e precisa ser consolidado neste arquivo.

09Erros comuns e como evitar
⚠
Pedir ao Developer para mudar a arquitetura — se a implementação exige mudança arquitetural, volte ao bmad-architect, atualize o documento, e então retome com o Developer. Pular isso gera divergência silenciosa.
⚠
Rodar DS sem project-context.md — sem ele, o agente toma decisões genéricas que podem conflitar com os padrões do projeto. Crie o arquivo antes de começar o primeiro DS.
⚠
Usar QD para features complexas — o Quick Dev não tem contexto arquitetural suficiente para mudanças grandes. Se a tarefa toca múltiplos módulos ou banco de dados, use o fluxo completo com DS.
⚠
Pular o CR — o Code Review não é burocracia. É o mecanismo que impede que problemas do agente (lógica errada, critérios não cobertos) cheguem ao QA e ao commit.
⚠
Stories muito grandes para DS — se uma story demora mais de 4 horas para implementar, o agente vai perder contexto no meio. Use CS para quebrar a story em partes menores antes de usar DS.
