02O que é BMAD

Metodologia de desenvolvimento orientada por IA baseada em agentes especializados, contexto estruturado, documentação versionada, contratos compartilhados e fluxo colaborativo.

Objetivo central

O objetivo NÃO é substituir pessoas, mas ampliar a capacidade do time, reduzir perda de contexto, aumentar consistência e acelerar execução.

03Objetivos do BMAD
Problemas que resolve
  • Contexto espalhado
  • Documentação inexistente
  • Dependência de pessoas-chave
  • Desalinhamento frontend/backend
  • Perda de decisões arquiteturais
  • Retrabalho e inconsistência
04Quando BMAD faz sentido
✅ Contextos ideais
  • Tiny teams
  • Produtos complexos
  • APIs enterprise
  • Times altamente técnicos
  • Sistemas com muitas regras de negócio
  • Integração forte frontend/backend

08PRD — Product Requirements Document

Documento funcional: problema, objetivos, regras, requisitos e comportamento esperado.

Estrutura recomendada
  1. Objetivo
  2. Problema
  3. Escopo
  4. Regras de negócio
  5. Fluxos
  6. Critérios de aceite
  7. Requisitos funcionais
  8. Requisitos não funcionais
09ADR — Architecture Decision Record

Registra decisões arquiteturais, contexto, tradeoffs e impactos — garante rastreabilidade total.

Estrutura recomendada
  1. Título
  2. Status (proposed / accepted / deprecated)
  3. Contexto
  4. Decisão
  5. Consequências
  6. Alternativas consideradas
  7. Referências

11Context Engineering

Processo de estruturar, versionar e compartilhar conhecimento para que a IA receba contexto correto em cada etapa.

📐
Estruturar
PRD, ADR, OpenAPI, claude.md em artefatos claros
📦
Versionar
Todo contexto no Git com histórico auditável
🔗
Compartilhar
Context repo central como fonte da verdade
12Organização de repositórios

Dois modelos: Monorepo e Multirepo. A escolha depende do time, pipelines e necessidade de deploy independente.

13Estratégia Monorepo
Estrutura
produto/
├── apps/
│   ├── backend/
│   └── frontend/
└── docs/
    ├── contracts/
    ├── adr/
    └── .ai/
✅ Fazer
  • Um único Git repository
  • Pipelines separadas por path
❌ Evitar
  • Múltiplos .git internos
  • Nested repositories
14Estratégia Multirepo
Estrutura
produto-context/
produto-backend/
produto-frontend/
Melhor prática
  • Context repo centralizado
  • Workspace compartilhado
  • Pipelines independentes por repo
15Context Repository

O cérebro do produto — fonte da verdade e camada compartilhada de contexto.

Estrutura
context-repo/
├── docs/
├── contracts/     ← OpenAPI e contratos
├── adr/           ← Architecture Decision Records
├── .ai/           ← Contexto para agentes IA
├── flows/         ← Fluxos de negócio
└── stories/       ← Stories e epics
16Estrutura ideal dos projetos
Workspace multirepo
workspace/
├── produto-context/     ← fonte da verdade
├── produto-backend/     ← API e serviços
└── produto-frontend/    ← interface e UX
17Estrutura de contexto para IA
Pasta .ai/ por escopo
.ai/
├── shared/
│   └── company-standards.md
├── backend/
│   └── backend-agent.md
└── frontend/
    └── angular-guidelines.md

Cada agente recebe apenas o contexto necessário — evita poluição e respostas genéricas.

18Fluxo operacional do time
🏗
Macro — sequencial
Discovery → PRD → ADR → OpenAPI → Implementação → QA → Deploy.
⚡
Micro — paralelo
Com OpenAPI definido, backend e frontend trabalham em paralelo sem bloqueio.
19Integração com pipelines corporativas
Manter
  • Pipelines independentes por serviço
  • Deploy separado por repo
Adicionar
  • Context repo compartilhado
  • OpenAPI centralizado
  • Workspace compartilhado
20Melhores práticas
✅
OpenAPI First — defina contratos antes de implementar
✅
Context-first development — estruture o contexto antes de invocar qualquer agente
✅
ADRs curtos e objetivos — documente decisões no momento em que são tomadas
✅
PRD versionado — trate o PRD como código, com histórico e revisões
✅
IA contextualizada — forneça o contexto correto antes de qualquer prompt
✅
Contratos centralizados — um único lugar para OpenAPI, acessível a todos
✅
Padrões corporativos compartilhados — .ai/shared/company-standards.md
21O que evitar
❌
IA sem contexto — gera alucinações e código inconsistente
❌
OpenAPI apenas no backend — frontend perde a fonte da verdade
❌
Regras fora do Git — decisões em Slack, e-mail ou cabeças de pessoas
❌
Documentação desconectada — docs que não acompanham o código ficam obsoletos
❌
Duplicação manual de contexto — cada repo replicando as mesmas regras
❌
Nested repositories — múltiplos .git dentro de um mesmo repo
