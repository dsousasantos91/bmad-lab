02 O que é BMAD

BMAD é uma metodologia de desenvolvimento orientada por IA baseada em agentes especializados, contexto estruturado, documentação versionada, contratos compartilhados e fluxo colaborativo.

Objetivo central

O objetivo NÃO é substituir pessoas. BMAD existe para ampliar a capacidade do time, reduzir perda de contexto, aumentar consistência e acelerar execução.

03 Objetivos do BMAD

O BMAD resolve problemas comuns em times pequenos:

Problemas que resolve
  • Contexto espalhado
  • Documentação inexistente
  • Dependência de pessoas-chave
  • Desalinhamento entre frontend e backend
  • Perda de decisões arquiteturais
  • Retrabalho e inconsistência técnica

08 PRD — Product Requirements Document

Documento funcional que descreve problema, objetivos, regras, requisitos e comportamento esperado.

Estrutura recomendada
  1. Objetivo
  2. Problema
  3. Escopo
  4. Regras de negócio
  5. Fluxos
  6. Critérios de aceite
  7. Requisitos funcionais
  8. Requisitos não funcionais
09 ADR — Architecture Decision Record

Documento responsável por registrar decisões arquiteturais, contexto, tradeoffs e impactos. Garante rastreabilidade total de "por que chegamos aqui".

Estrutura recomendada
  1. Título
  2. Status (proposed / accepted / deprecated)
  3. Contexto
  4. Decisão
  5. Consequências
  6. Alternativas consideradas
  7. Referências

11 Context Engineering

Context Engineering é o processo de estruturar, versionar e compartilhar conhecimento para que a IA receba o contexto correto em cada etapa. É o diferencial entre uma IA que "chuta" e uma IA que age como membro do time.

📐
Estruturar
Organizar conhecimento em artefatos claros: PRD, ADR, OpenAPI, claude.md
📦
Versionar
Todo contexto vive no Git. Decisões têm histórico e são auditáveis
🔗
Compartilhar
Um context repo central serve como fonte da verdade para todos os agentes e devs
12 Organização de repositórios

Dois modelos principais: Monorepo e Multirepo. A escolha depende do tamanho do time, das pipelines corporativas e da necessidade de deploy independente.

13 Estratégia Monorepo
Estrutura recomendada
produto/
├── apps/
│   ├── backend/
│   └── frontend/
│
└── docs/
    ├── contracts/
    ├── adr/
    └── .ai/
✅ Fazer
  • Um único Git repository
  • Pipelines separadas por path
❌ Evitar
  • Múltiplos .git internos
  • Nested repositories
14 Estratégia Multirepo
Estrutura recomendada
produto-context/
produto-backend/
produto-frontend/
Melhor prática
  • Context repo centralizado e compartilhado
  • Workspace compartilhado entre os repos
  • Pipelines independentes por repo
15 Context Repository

O context repo é o cérebro do produto — fonte da verdade e camada de contexto compartilhada entre todos os times e agentes de IA.

Estrutura recomendada
context-repo/
├── docs/
├── contracts/     ← OpenAPI e contratos
├── adr/           ← Architecture Decision Records
├── .ai/           ← Contexto para agentes IA
├── flows/         ← Fluxos de negócio
└── stories/       ← Stories e epics
16 Estrutura ideal dos projetos
Exemplo workspace multirepo
workspace/
├── produto-context/     ← fonte da verdade
├── produto-backend/     ← API e serviços
└── produto-frontend/    ← interface e UX
17 Estrutura de contexto para IA
Pasta .ai/ por escopo
.ai/
├── shared/
│   └── company-standards.md   ← padrões globais
├── backend/
│   └── backend-agent.md       ← contexto do backend
└── frontend/
    └── angular-guidelines.md  ← contexto do frontend

Cada agente recebe apenas o contexto necessário para sua tarefa — evitando poluição de contexto e respostas genéricas.

18 Fluxo operacional do time
🏗
Macro — fluxo sequencial
Discovery → PRD → ADR → OpenAPI → Implementação → QA → Deploy. Cada etapa depende da anterior e gera artefatos que alimentam a próxima.
⚡
Micro — trabalho paralelo
Com os contratos (OpenAPI) definidos, backend e frontend trabalham em paralelo de forma autônoma, sem bloqueio mútuo.
19 Integração com pipelines corporativas
Manter
  • Pipelines independentes por serviço
  • Deploy separado por repositório
Adicionar
  • Context repo compartilhado
  • OpenAPI centralizado
  • Workspace compartilhado
20 Melhores práticas
✅
OpenAPI First — defina contratos antes de implementar
✅
Context-first development — estruture o contexto antes de invocar qualquer agente
✅
ADRs curtos e objetivos — documente decisões no momento em que são tomadas
✅
PRD versionado — trate o PRD como código, com histórico e revisões
✅
IA contextualizada — sempre forneça o contexto correto antes de qualquer prompt
✅
Contratos centralizados — um único lugar para OpenAPI, acessível a todos
✅
Padrões corporativos compartilhados — .ai/shared/company-standards.md
21 O que evitar
❌
IA trabalhando sem contexto — gera alucinações e código inconsistente
❌
OpenAPI apenas no backend — frontend perde a fonte da verdade
❌
Regras fora do Git — decisões em Slack, e-mail ou cabeças de pessoas
❌
Documentação desconectada — docs que não acompanham o código ficam obsoletos
❌
Duplicação manual de contexto — cada repo replicando as mesmas regras manualmente
❌
Nested repositories complexos — múltiplos .git dentro de um mesmo repo
