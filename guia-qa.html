BMAD para QAs

Como usar o BMAD para garantir qualidade em projetos greenfield e brownfield — desde a geração automática de testes até o Test Architect Enterprise para projetos de alto risco.
QA Test Architect Brownfield Quality Gates E2E Tests Regressão
01QA no BMAD v6 — como está estruturado

No BMAD v6, o sistema de QA tem dois níveis com escopos bem diferentes. Entender qual usar é o primeiro passo para não sobre-engenheirar o processo.

⚡
Nível 1 — BMM base
Geração de testes E2E via Developer Agent (Amelia). Disponível em qualquer projeto sem instalação adicional. Ideal para greenfield e features novas.
🏗
Nível 2 — TEA Module
Test Architect Enterprise. Módulo separado com agente dedicado (Quinn) para projetos brownfield, código legado e sistemas de alto risco.

A regra geral: projetos novos ou features sem código legado usam o Nível 1. Qualquer coisa que toque código existente, legado ou sistemas críticos deve usar o Nível 2.

02QA via Developer Agent — geração automática de testes

O trigger QA do Developer Agent (bmad-agent-dev) aciona o workflow bmad-qa-generate-e2e-tests. Ele analisa o codebase implementado e gera uma suite de testes completa automaticamente.

O que o workflow faz automaticamente
  • Detecção de framework — escaneia o package.json procurando Jest, Vitest, Playwright ou Cypress. Se nenhum existir, analisa a stack e sugere um
  • Testes de API — cobre status codes, estrutura da resposta, happy path e casos críticos de erro
  • Testes E2E — foca em workflows do usuário usando locators semânticos (roles, labels, texto visível)
  • Checklist de validação — verifica que os testes não têm waits fixos (sleep), são independentes entre si e usam APIs padrão do framework
Como usar no Dev Loop
DS implementa
→
CR revisa
→
QA gera testes
→
testes passam
→
commit

O trigger QA deve ser usado após CR (Code Review) para que a revisão já tenha corrigido problemas óbvios antes da geração dos testes.

03Test Architect (TEA) — para brownfield e alto risco

O Test Architect Enterprise é um módulo separado do BMAD que adiciona o agente Quinn com capacidades avançadas de análise de risco, planejamento de regressão e rastreamento de requisitos. É indispensável quando o trabalho toca código existente.

Instale o TEA quando trabalhar em projetos brownfield: npx bmad-method install --module tea
🎯
Análise de risco
Identifica regressões potenciais, dependências legadas e breaking changes antes de qualquer implementação
🗺
Planejamento de testes
Projeta a estratégia de cobertura de regressão com base no risco mapeado
🔗
Rastreabilidade
Mapeia cada requisito do PRD para os testes que o cobrem — evidência auditável
📋
NFR validation
Valida requisitos não funcionais: performance, segurança, acessibilidade
04Triggers do Test Architect (TEA)

O TEA tem triggers específicos para cada etapa do ciclo de QA em projetos brownfield. A sequência importa — *risk sempre vem antes de *design.

TriggerNomeQuando usar
@qa *risk Risk Assessment Antes de qualquer implementação que toque código existente. Identifica regressões potenciais e dependências legadas obrigatório
@qa *design Test Design Após o risk assessment. Projeta a estratégia de cobertura de regressão com base nos riscos mapeados obrigatório
@qa *trace Requirements Trace Mapeia cada requisito do PRD para os testes correspondentes. Essencial para auditoria e compliance obrigatório
@qa *nfr NFR Validation Valida requisitos não funcionais: performance, segurança, acessibilidade, escalabilidade obrigatório
@qa *review Full Review Após o desenvolvimento completo da story. Análise profunda + refatoração ativa. Gera arquivo de resultado e gate obrigatório
@qa *gate Gate Status Update Após corrigir os problemas apontados no review. Atualiza a decisão do quality gate pós-correção

O gate pode waive (aceitar) issues de código legado, documentando explicitamente a aceitação de dívida técnica e rastreando o progresso de migração.

06Quality Gates — o que são e como funcionam

Quality gates são checkpoints de transição entre fases do workflow. Cada gate verifica que os artefatos da fase anterior atendem critérios definidos antes de avançar. Eles não são burocracia — são o mecanismo que impede que problemas do agente se acumulem entre sprints.

📐
Architect → Developer
O documento de arquitetura precisa satisfazer critérios específicos antes do Developer começar a implementação
✅
Developer → QA
Cobertura de testes e critérios de aceite precisam estar atendidos antes do QA aprovar a story
🚀
QA → Merge
O quality gate file em docs/qa/gates/ precisa estar aprovado ou com waive documentado
Princípio central: cada agente no BMAD produz um artefato verificável, não apenas uma resposta de chat. PRDs, arquiteturas, planos de teste e stories são documentos persistentes que podem ser revisados, versionados e auditados — exatamente como artefatos de software reais.
07Quando o TEA é obrigatório vs recomendado

Use esta árvore de decisão para definir o nível de QA necessário:

O código toca código legado ou sistemas existentes?
SIM → TEA é obrigatório — rode *risk, *design e *review no mínimo
NÃO → Continue para a próxima pergunta
O enhancement afeta múltiplos sistemas ou é uma mudança maior?
SIM → TEA é obrigatório — rode TEA antes de qualquer implementação
NÃO → Continue para a próxima pergunta
É mais do que um bug fix simples (uma feature pequena)?
SIM → TEA é recomendado — rode pelo menos *risk nos pontos de integração
NÃO → TEA é opcional — mas rode *risk se tocar caminhos críticos
🔴
Obrigatório — toca código legado, mudança maior, múltiplos sistemas. Rode: *risk + *design + *review + *gate
🟡
Recomendado — feature pequena sem código legado. Rode pelo menos: *risk + *review
🟢
Opcional — bug fix simples sem caminhos críticos. QA via Developer Agent (QA trigger) é suficiente
08Party Mode — múltiplos agentes revisando juntos

O BMAD tem o skill bmad-party-mode que orquestra discussões entre múltiplos agentes especializados numa mesma sessão. Para QA, o caso mais útil é colocar Winston (Architect) e Amelia (Developer) para debater uma implementação antes do QA formal.

O detalhe técnico importante: cada agente é iniciado como um subagente separado, evitando a "convergência de opinião" que acontece quando um único LLM simula múltiplos personagens. Isso garante perspectivas genuinamente independentes.

Quando usar Party Mode no ciclo de QA
  • Antes de uma story complexa — Architect e Developer alinham expectativas antes da implementação
  • Durante code review de mudanças arquiteturais — Architect valida se o código respeita as decisões de design
  • Em postmortems de bugs — múltiplos agentes analisam causas raiz de perspectivas diferentes
  • Para validar strategy de testes — QA e Architect discutem cobertura necessária
09Edge Case Hunter — encontrando o que você não pensou

O bmad-review-edge-case-hunter é uma task especializada que realiza rastreamento metódico de caminhos para encontrar condições não tratadas, erros de boundary e race conditions. É diferente do QA normal — ele busca ativamente o que pode dar errado, não apenas valida o que deveria funcionar.

🎯
Casos de boundary
Valores no limite de ranges, strings vazias, arrays com zero elementos, números máximos de tipo
⚡
Race conditions
Operações concorrentes, estado compartilhado, timeouts e retries em operações assíncronas
🔍
Caminhos não tratados
Combinações de inputs válidos que chegam em estado inválido, fluxos alternativos não documentados

Use o Edge Case Hunter antes do *review formal em stories críticas — especialmente em funcionalidades financeiras, autenticação, processamento de dados ou qualquer fluxo onde um edge case pode ter impacto de produção.
