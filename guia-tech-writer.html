00O papel humano nesta fase

Documentação é o artefato que mais sofre com a pressão de prazo — e o que mais custa caro quando inexistente. A Paige acelera a produção de documentação, mas não substitui o julgamento sobre o que documentar, para quem e com qual nível de detalhe.

O agente não sabe quais partes do sistema são frágeis e merecem documentação extra. Não sabe qual é o nível técnico do leitor. Não sabe quais decisões foram tomadas em reunião e nunca viraram artefato. Essas são contribuições humanas insubstituíveis — com ou sem um Tech Writer dedicado.

🧠
Você traz
Conhecimento do leitor, contexto de negócio, julgamento sobre profundidade, decisões não documentadas e validação da clareza do texto gerado
⚡
Paige traz
Velocidade de escrita, consistência de formato, cobertura sistemática de tópicos, templates estruturados e adaptação de tom por tipo de documento
Princípio central: documentação boa não é documentação completa — é documentação útil para quem vai lê-la. Sua principal tarefa ao operar a Paige é garantir que o output serve o leitor real, não apenas cobre o conteúdo técnico.
01Paige — o agente Tech Writer

A Paige é o agente de documentação técnica do BMAD. Ela adapta tom, formato e profundidade conforme o tipo de documento — um README para desenvolvedores é diferente de release notes para usuários finais, que é diferente de um guia de API para integradores.

📖
Documentação técnica
READMEs, guias de API, documentação de arquitetura, guias de contribuição e onboarding para devs
📋
Documentação de produto
Release notes, changelogs, guias de usuário, FAQs e documentação de features para usuários finais
🔗
Documentação de processo
Runbooks, guias operacionais, playbooks de incidente e documentação de deploy
📐
Documentação de padrões
Style guides, coding standards, convenções de projeto e guias de decisão arquitetural
02Triggers disponíveis

A Paige tem triggers cobrindo os tipos mais comuns de documentação que surgem ao longo do ciclo BMAD.

TriggerNomeO que gera
DR Doc README README completo do projeto — visão geral, instalação, uso, contribuição e licença. Adapta o nível técnico conforme o público informado
DA Doc API Documentação de API baseada nos contratos definidos na arquitetura — endpoints, parâmetros, respostas, exemplos e erros
RN Release Notes Release notes estruturadas a partir das stories e epics concluídos — novas features, correções, breaking changes e instruções de migração
CL Changelog Changelog versionado seguindo o padrão Keep a Changelog, gerado a partir do histórico de stories e commits
GU Guide User Guia de usuário para uma feature ou fluxo específico — passo a passo, screenshots placeholders e casos comuns de uso
RB Runbook Runbook operacional — procedimentos de deploy, rollback, diagnóstico de incidentes e checklists de operação
SG Style Guide Style guide de documentação ou código — convenções de nomenclatura, formato de commits, padrões de comentário e tom de escrita
03Tiny team — quem opera a Paige?

Em tiny teams, não há um Tech Writer dedicado. A responsabilidade é distribuída por quem produziu o artefato que precisa ser documentado — o princípio é simples: quem criou, documenta.

Tabela de responsabilidade por tipo de doc
DocumentoQuem opera PaigeTrigger
README do projeto Dev DR
Documentação de API Dev DA
Guia de contribuição Dev SG
Runbook / deploy guide Dev RB
Release notes PM RN
Changelog PM CL
Guia de usuário PM GU
Documentação de arquitetura Architect SG + manual
ADRs legíveis por não-técnicos Architect GU
Regra de ouro tiny team: nunca termine uma story sem acionar ao menos o trigger DR ou DA se a story adicionou ou modificou comportamento público. Documentação não é uma tarefa separada — é o último passo de cada story.
04Dev operando a Paige

O Developer é quem mais aciona a Paige no dia a dia. Após implementar e fazer code review, antes do commit final, aciona a documentação técnica da feature.

Quando acionar no Dev Loop
DS implementa
→
CR revisa
→
Paige documenta
→
commit
O que passar como contexto
  • A story implementada — a Paige usa os critérios de aceite como base do que documentar
  • Os contratos de API modificados ou criados — input direto para o trigger DA
  • O project-context.md — garante que a documentação segue as convenções do projeto
  • O público-alvo do documento — dev interno, dev externo, usuário final ou ops
O que o Dev deve revisar antes de commitar
  • Exemplos de código estão corretos e funcionam?
  • Nomes de variáveis, endpoints e parâmetros batem com o código real?
  • Há informação sensível (tokens, URLs internas) que não deveria estar no doc?
  • O nível de detalhe é adequado para o leitor — não falta nem sobra?
05PM operando a Paige

O PM aciona a Paige ao final de cada sprint ou release para produzir a documentação voltada ao usuário e ao negócio.

Quando acionar no ciclo de produto
Epic concluído
→
RN / CL
→
GU
→
release
Release notes — o que passar como contexto
  • Lista de stories e epics concluídos no período — a Paige transforma em linguagem de usuário
  • Breaking changes identificados pelo Architect ou Developer
  • Instrução de migração se houver mudança de contrato ou modelo de dados
  • Tom da release: patch silencioso, minor com novas features ou major com mudanças de produto
Dica: ao usar o trigger RN, diga à Paige explicitamente para quem são as release notes — desenvolvedores que integram a API têm necessidades diferentes de usuários finais do produto. O tom e o nível de detalhe mudam completamente.
06Architect operando a Paige

O Architect aciona a Paige para tornar decisões técnicas compreensíveis para audiências não-técnicas — stakeholders, novos membros do time ou documentação de produto de longo prazo.

Casos de uso do Architect com a Paige
  • ADRs em linguagem acessível — transformar um ADR técnico num resumo executivo que stakeholders não-técnicos conseguem ler e aprovar
  • Guia de onboarding de devs — documentação que explica a arquitetura para um dev novo no projeto sem precisar de par programming
  • Style guide de código — transformar as convenções do project-context.md em um guia oficial do projeto usando SG
  • Documentação de integrações — explicar como sistemas externos se conectam ao produto para times de parceiros ou integradores

08Tech Writer dedicado — o papel

Quando existe um Tech Writer dedicado, a relação com a Paige muda: em vez de ser acionada de forma reativa por quem produziu o artefato, a Paige vira a ferramenta principal de uma pessoa que pensa em documentação de forma estratégica e proativa.

O Tech Writer dedicado não apenas produz docs — ele define o que precisa ser documentado, como o sistema de documentação está organizado e garante que a documentação está sempre sincronizada com o produto real.

🗺
Doc strategy
Define a arquitetura de informação do produto: quais docs existem, para quem, em qual formato e onde vivem
🔄
Doc lifecycle
Garante que docs são criados, atualizados e depreciados junto com o produto — não ficam desatualizados após releases
📏
Style & standards
Define e mantém o style guide de documentação que toda a Paige vai usar como referência consistente
🤝
Revisão editorial
Revisa o output da Paige antes de publicar — garante clareza, tom adequado e ausência de jargão desnecessário
09Fluxo com Tech Writer dedicado

Com um TW dedicado, a documentação deixa de ser um passo no fim de cada story e vira uma disciplina paralela ao desenvolvimento:

Fase de planejamento — TW participa do PRD
  • Lê o PRD e identifica quais features vão precisar de documentação de usuário
  • Aciona a Paige com GU para criar o esqueleto do guia de usuário já no início do ciclo — não no final
  • Alinha com o PM o tom e o público-alvo de cada tipo de doc
Fase de desenvolvimento — TW trabalha em paralelo
Dev implementa story
→
TW: Paige DA / DR
→
TW revisa e publica
  • TW acompanha as stories concluídas em tempo real e documenta sem esperar o release
  • Usa o ticket da story como contexto para a Paige — mantém rastreabilidade entre feature e doc
  • Coordena com o Dev para validar exemplos de código antes de publicar
Fase de release — TW fecha o ciclo
PM fecha epic
→
TW: Paige RN + CL
→
TW: revisão editorial
→
publicação coordenada
10Doc strategy — construindo o sistema de documentação

O Tech Writer dedicado usa a Paige com o trigger SG para criar e manter o style guide de documentação do produto. Este guia vira o input padrão para todas as sessões futuras com a Paige — garantindo consistência mesmo quando diferentes pessoas acionam o agente.

O que o style guide de documentação deve conter
  • Tom e voz — formal, conversacional, técnico ou acessível? Como tratamos o leitor (você, usuário, desenvolvedor)?
  • Estrutura por tipo — qual é o template de um README, de um guia de API, de um runbook?
  • Convenções de nomenclatura — como nomear arquivos de doc, seções e headings?
  • Exemplos — quando incluir, como formatar, como nomear variáveis de exemplo
  • O que evitar — jargão interno, siglas não explicadas, pronomes ambíguos
  • Processo de revisão — quem aprova cada tipo de doc antes de publicar
Como usar o style guide com a Paige: adicione ao claude.md do projeto: "Documentation style guide is located at docs/style-guide.md. All documentation must follow this guide." Assim todos os agentes carregam o guia automaticamente quando geram documentação.
11Tipos de documentação — referência rápida
📘
README
Trigger: DR · Quem: Dev
Visão geral, instalação, uso básico, contribuição. Público: qualquer dev que encontra o repositório
🔌
API Docs
Trigger: DA · Quem: Dev
Endpoints, parâmetros, respostas e exemplos. Público: devs que integram a API
📣
Release Notes
Trigger: RN · Quem: PM / TW
Novas features, correções, breaking changes por release. Público: usuários e integradores
📋
Changelog
Trigger: CL · Quem: PM / TW
Histórico versionado de todas as mudanças. Formato: Keep a Changelog
📗
User Guide
Trigger: GU · Quem: PM / TW
Passo a passo de uso de uma feature. Público: usuário final do produto
🔧
Runbook
Trigger: RB · Quem: Dev / TW
Procedimentos de deploy, rollback e incidente. Público: time de ops e devs em plantão
📏
Style Guide
Trigger: SG · Quem: TW / Architect
Convenções de código, documentação e processo. Público: todo o time
12Erros comuns e como evitar
❌
Deixar documentação para depois do deploy — "vamos documentar quando tiver tempo" é uma promessa que nunca é cumprida. Doc é o último passo de cada story, não uma tarefa separada do backlog.
❌
Aceitar o output da Paige sem revisar exemplos de código — o agente gera exemplos plausíveis mas pode usar nomes de variáveis ou endpoints que não batem com o código real. Sempre valide exemplos antes de publicar.
❌
Documentação sem audiência definida — "escreva a documentação da feature X" sem especificar o leitor gera um texto que não serve bem a ninguém. Sempre diga à Paige para quem o documento é.
⚠
Não versionar docs junto com o código — documentação fora do repositório se desincroniza rapidamente. Mantenha tudo em docs/ e commite junto com o código que documenta.
⚠
Tiny team sem um "dono" de docs — mesmo sem TW dedicado, alguém precisa ser responsável pela saúde do sistema de documentação. Defina quem revisa a qualidade geral a cada sprint — pode ser o PM ou o tech lead.
