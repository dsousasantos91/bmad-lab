01O papel do humano na fase de arquitetura

A fase de arquitetura é onde as decisões técnicas de longo prazo são tomadas. O Architect Agent (Winston) estrutura e documenta essas decisões, mas as escolhas fundamentais são humanas — não deixe o agente escolher a stack, o modelo de dados ou os contratos de API sem sua aprovação explícita.

Winston é excelente em: identificar implicações de uma decisão, documentar tradeoffs, gerar estruturas de pastas e contratos de API, e manter consistência entre partes da arquitetura. Ele não é excelente em: saber as restrições não documentadas do seu ambiente, entender dívida técnica histórica ou tomar decisões políticas sobre tecnologia.

🏗
Você decide
Stack tecnológica, padrões de design, limites de serviço, contratos públicos, estratégia de migração
⚡
Winston estrutura
Documentação das decisões, tradeoffs explicitados, diagrama de componentes, estrutura de pastas, contratos de API
02Winston — triggers disponíveis

O Architect tem 2 triggers principais no módulo BMM base. A simplicidade é intencional — o trabalho de arquitetura é profundo, não amplo.

TriggerNomeQuando usar
CA Create Architecture Cria o documento de arquitetura a partir do PRD aprovado. Input principal: o PRD completo como contexto na sessão. Para brownfield, use o template de arquitetura brownfield
IR Implementation Readiness Checklist formal que verifica se a arquitetura está completa e consistente o suficiente para o Developer começar. Use antes de gerar as stories. Compartilhado com o PM
Nota sobre brownfield: para projetos existentes, o Architect também usa o trigger DP (Document Project) junto com o Analyst para documentar o codebase antes de propor mudanças. E usa o template brownfield-architecture-tmpl no lugar do template padrão no trigger CA.
03Criando a arquitetura (CA) — como conduzir bem

O trigger CA inicia um workflow estruturado. Winston vai explorar o PRD e propor decisões arquiteturais em sequência. Sua responsabilidade é aprovar, ajustar ou rejeitar cada proposta com justificativa.

O que Winston vai propor e você deve validar
  • Stack tecnológica — linguagem, framework, banco de dados, infra. Valide contra as restrições reais do seu ambiente
  • Estrutura de componentes — como os módulos se relacionam, quais são os limites de cada serviço
  • Contratos de API — endpoints, payloads, autenticação. Aprove explicitamente antes de continuar
  • Modelo de dados — entidades, relacionamentos, estratégia de persistência
  • Decisões de segurança — autenticação, autorização, criptografia
  • Estratégia de deploy — como o sistema vai para produção e como escala
Dica de operação: quando Winston propuser algo que você não concorda, não apenas diga "não". Explique a restrição ou contexto que ele não sabe — isso melhora a próxima proposta. Ex: "Não podemos usar PostgreSQL porque o ambiente corporativo só permite Oracle. Proponha alternativa."
Perguntas que você deve fazer ao Winston durante CA
  • "Quais são os principais riscos desta decisão arquitetural?"
  • "Que alternativas você considerou para X? Por que descartou?"
  • "Como esta arquitetura escala se o volume triplicar em 6 meses?"
  • "Quais pontos desta arquitetura criam acoplamento forte entre módulos?"
  • "O que nesta arquitetura vai ser mais difícil de mudar depois?"
04O documento de arquitetura — o que deve conter

O documento de arquitetura é o artefato central que alimenta o Developer. Quanto mais claro e completo, menos ambiguidade nas stories e menos retrabalho no código.

Estrutura mínima
docs/architecture.md

## Visão geral
Descrição em 1 parágrafo do sistema e seus objetivos técnicos

## Stack tecnológica
Linguagem, framework, banco, infra — com versões e justificativas

## Diagrama de componentes
Relação entre módulos, serviços e dependências externas

## Contratos de API
Endpoints, métodos, payloads, códigos de resposta e autenticação

## Modelo de dados
Entidades principais, relacionamentos e estratégia de persistência

## Decisões arquiteturais (ADRs)
Lista com links ou inline das decisões e seus tradeoffs

## Estrutura de pastas
Organização do código com convenções de nomenclatura

## Considerações de segurança
Autenticação, autorização, dados sensíveis, pontos de atenção

## Estratégia de deploy e escala
Como o sistema vai a produção e como responde ao crescimento

Salve como docs/architecture.md e faça commit. Este arquivo é o input para todas as stories geradas pelo PM via CE e pelo Developer via CS.

05ADRs — Architecture Decision Records

ADRs são a memória viva da arquitetura. Cada decisão significativa — especialmente as não óbvias — deve ter um ADR. Eles respondem a pergunta mais comum em projetos: "por que fizemos dessa forma?"

ADR-001 — Exemplo de estrutura
Título: Usar PostgreSQL como banco principal
Status: accepted
Contexto: O produto precisa de transações ACID para operações financeiras e suporte nativo a JSON para dados de configuração variável por cliente.
Decisão: PostgreSQL 15 com pgvector para buscas semânticas futuras.
Consequências: Operações de leitura intensiva precisarão de índices bem planejados. Time precisa de familiaridade com SQL avançado.
Alternativas consideradas: MongoDB (descartado por falta de ACID nativo), MySQL (descartado por suporte inferior a JSON).
Quando criar um ADR
  • Toda escolha de stack (linguagem, framework, banco, infra)
  • Qualquer decisão que envolva tradeoff significativo
  • Padrões de design que o time deve seguir consistentemente
  • Decisões que foram difíceis ou tiveram debate interno
  • Qualquer coisa que, se mudada no futuro, terá impacto amplo
Como pedir ao Winston para gerar ADRs: durante ou após o CA, diga "Gere um ADR para a decisão de [X] seguindo a estrutura padrão". Salve em docs/adr/ADR-NNN-titulo.md com numeração sequencial.
06Implementation Readiness (IR)

O trigger IR é o gate formal antes de passar a arquitetura para o Developer. Ele verifica que todos os artefatos necessários estão presentes e consistentes entre si.

O que o IR verifica
  • PRD e arquitetura estão consistentes — sem contradições entre requisitos e decisões técnicas
  • Todos os requisitos funcionais têm correspondência na arquitetura
  • NFRs (performance, segurança) têm estratégia técnica definida
  • Contratos de API estão completos o suficiente para frontend e backend trabalharem em paralelo
  • Estrutura de pastas e convenções de código estão documentadas
  • Dependências externas e integrações estão mapeadas
Importante: o IR é compartilhado entre PM e Architect. Se o IR revelar lacunas no PRD, volte ao PM antes de prosseguir. Se revelar lacunas na arquitetura, corrija a arquitetura. Não prossiga com o Developer se o IR tiver falhas críticas.
07Brownfield — Document Project (DP)

Em projetos existentes, o primeiro passo do Architect é entender o sistema antes de propor mudanças. O trigger DP (compartilhado com o Analyst) analisa o codebase e gera documentação estruturada que serve de input para a arquitetura brownfield.

O que o DP gera em docs/
docs/
├── index.md              ← ponto de entrada obrigatório
├── project-overview.md   ← resumo executivo e stack atual
├── architecture.md       ← arquitetura existente documentada
├── source-tree-analysis.md
├── api-contracts.md      ← endpoints existentes
└── data-models.md        ← schemas e modelos atuais
O que você deve revisar e complementar
  • Dívida técnica que o agente não conseguiu inferir do código
  • Decisões históricas que não estão documentadas mas importam
  • Integrações externas não óbvias no código
  • Restrições de ambiente (cloud provider, versões fixas, licenças)
  • Convenções não escritas que o time segue na prática
08Arquitetura brownfield — foco em integração

Em projetos existentes, a arquitetura não começa do zero — ela adapta o sistema existente para suportar a nova funcionalidade sem quebrar o que já funciona. A mentalidade muda de "como projetar" para "como encaixar".

Use o template brownfield no CA

Ao acionar o CA em um projeto brownfield, informe explicitamente ao Winston: "Este é um projeto brownfield. Use o template de arquitetura brownfield e foque nos pontos de integração com o sistema existente."

O template brownfield inclui seções adicionais:

  • Pontos de integração — onde o novo código se conecta ao existente
  • Estratégia de migração — como dados e funcionalidades existentes são preservados
  • Riscos de regressão — o que pode quebrar e como mitigar
  • Dívida técnica reconhecida — o que não vai ser resolvido agora mas foi documentado
Regra de ouro no brownfield

Nunca proponha uma arquitetura que exija mudanças em partes do sistema que não estão no escopo da feature. Se a feature nova requer mudança arquitetural ampla, isso deve ser um epic separado — não um efeito colateral silencioso da implementação.

09Arquitetura que alimenta bem o Developer

A qualidade do trabalho do Developer depende diretamente da clareza da arquitetura. Estes são os elementos que mais impactam o Dev Loop:

✅
Contratos de API completos antes do código — com endpoints, payloads de request e response, códigos de erro e exemplos. Permite que frontend e backend trabalhem em paralelo sem bloqueio.
✅
Estrutura de pastas com convenções explícitas — onde cada tipo de arquivo vai, como nomear classes, interfaces e módulos. O Developer usa isso como referência em cada story.
✅
Limites entre módulos claramente definidos — o Developer precisa saber o que pertence a cada módulo e o que é compartilhado. Fronteiras ambíguas geram código acoplado.
✅
Decisões de tecnologia com versão fixada — Node 20.x, não "Node recente". TypeScript 5.3, não "TypeScript". Versões ambíguas geram ambientes inconsistentes.
⚠
Padrões de tratamento de erro documentados — como erros são propagados, logados e retornados ao cliente. Sem isso, cada Developer vai implementar diferente.
Gere o project-context.md após a arquitetura: rode bmad-generate-project-context após o CA para capturar automaticamente as decisões técnicas em formato que o Developer Agent carrega em cada sessão. É o complemento prático do documento de arquitetura.
10Party Mode com o Developer

O BMAD tem o skill bmad-party-mode que coloca Winston (Architect) e Amelia (Developer) para debater em conjunto. Para o Architect, os momentos mais valiosos de usar isso são:

🔍
Antes da implementação
Winston e Amelia alinham expectativas antes do DS. Frequentemente revela ambiguidades que o Architect não viu do lado da implementação
⚡
Code review arquitetural
Winston valida se o código da story respeita os limites e contratos definidos na arquitetura. Mais eficaz que um review manual
🏗
Decisões de refatoração
Quando o Developer encontra dívida técnica durante implementação, Party Mode ajuda a decidir se refatora agora ou documenta como ADR de dívida
11Erros comuns e como evitar
❌
Aprovar a arquitetura sem ler os ADRs — os ADRs contêm os tradeoffs que você vai viver com no futuro. Não aprovar sem entender o que está sendo decidido e por quê.
❌
Deixar contratos de API vagos — "campo de filtro opcional" não é um contrato. O Developer vai inventar o formato e o frontend vai inventar outro. Defina payload completo com exemplos.
❌
Não atualizar a arquitetura quando o PRD muda — se o PM usa CC para mudar escopo, a arquitetura precisa ser revisada. Nunca deixe PRD e arquitetura desalinhados — o Developer vai seguir a arquitetura, não o PRD.
⚠
Arquitetura excessivamente detalhada antes de validar premissas — se ainda há hipóteses não validadas no produto, não invista em arquitetura profunda de módulos que podem nem existir. Arquitete o suficiente para começar e itere.
⚠
Não gerar o project-context.md — o documento de arquitetura é rico mas longo demais para carregar em cada sessão do Developer. O project-context.md é o resumo executivo operacional — gere-o.
