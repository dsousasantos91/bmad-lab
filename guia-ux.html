00O papel humano nesta fase

Design é a disciplina que mais depende de contexto humano — e a que mais sofre quando esse contexto está ausente. A Sally estrutura fluxos, gera especificações e documenta decisões de interface, mas não tem como sentir a frustração de um usuário real, entender nuances culturais do seu público ou perceber que um fluxo tecnicamente correto é cognitivamente confuso na prática.

O papel do UX Designer humano no BMAD é ser o defensor do usuário dentro do ciclo de desenvolvimento. Você traz pesquisa, traz empatia e, principalmente, traz a capacidade de questionar soluções que parecem óbvias para o time técnico mas são opacos para quem vai usar o produto.

🧠
Você traz
Pesquisa de usuário, empatia, contexto cultural, julgamento sobre usabilidade e validação de que o fluxo funciona para pessoas reais
⚡
Sally traz
Estruturação de fluxos, especificações de componentes, documentação de estados e heurísticas de usabilidade aplicadas sistematicamente
Princípio central: UX no BMAD não é uma fase separada que acontece antes do desenvolvimento — é uma disciplina que atravessa todo o ciclo. A Sally deve ser acionada na descoberta, no planejamento, na arquitetura e no desenvolvimento. Quanto mais tarde o UX entra, mais caro é consertar.
01Sally — o agente UX Designer

A Sally é o agente de design de experiência do usuário do BMAD. Ela opera com foco em fluxos de usuário, especificações de interface e critérios de usabilidade — não em geração de assets visuais ou código CSS. Seu output são documentos que informam as decisões dos outros agentes.

🗺
User flows
Mapeamento de jornadas do usuário — happy path, caminhos alternativos e estados de erro
📐
Especificações
Documentação de componentes, estados, comportamentos e regras de interação
🔍
Heurísticas
Avaliação de usabilidade de fluxos e interfaces com base em princípios estabelecidos
🤝
Handoff docs
Documentação de interface pronta para o Developer implementar sem ambiguidade
02Triggers disponíveis

A Sally tem triggers cobrindo as etapas centrais do processo de UX dentro do ciclo BMAD.

TriggerNomeO que gera
UB UX Brief Documento de contexto de UX baseado no Project Brief — define público, objetivos de experiência, restrições de interface e princípios de design para o produto
UF User Flows Mapeamento completo dos fluxos de usuário — happy path, caminhos alternativos, estados de erro e transições entre telas
US UX Spec Especificação detalhada de uma tela ou componente — comportamentos, estados, regras de validação, mensagens de erro e acessibilidade
UH UX Heuristics Avaliação heurística de um fluxo ou interface usando as 10 heurísticas de Nielsen — identifica problemas de usabilidade antes do desenvolvimento
UD UX Handoff Documento de handoff para o Developer — especificação completa de uma feature pronta para implementação, sem ambiguidade de comportamento
UA UX Audit Auditoria de UX de um produto ou fluxo existente — identifica problemas, prioriza por impacto e propõe melhorias incrementais
03Onde UX entra no fluxo BMAD

UX não é uma fase — é uma disciplina transversal que contribui em cada etapa do ciclo BMAD. O erro mais comum é inserir o UX apenas entre o PRD e o desenvolvimento, perdendo a oportunidade de influenciar o produto quando o custo de mudança ainda é baixo.

Fase 1
Descoberta — junto com o Analyst
A Sally contribui com o UX Brief (UB) que documenta os objetivos de experiência do produto. Também avalia, junto ao Analyst, se o problema identificado tem implicações de usabilidade que o Brief deve capturar.
  • Acione a Sally com UB após o brainstorming do Analyst
  • Output: UX Brief que alimenta o PM e o Architect
Fase 2
Planejamento — junto com o PM
A Sally cria os user flows (UF) que validam se os requisitos do PRD são implementáveis de forma usável. Fluxos revelam lacunas no PRD que critérios de aceite textuais não capturam.
  • Acione a Sally com UF após o PRD inicial
  • Output: User flows que o PM usa para refinar o PRD e o QA usa como base de cenários
Fase 3
Arquitetura — junto com o Architect
A Sally valida se as decisões de arquitetura (especialmente de API e modelo de dados) suportam os fluxos de usuário projetados. Um modelo de dados que não suporta um estado de interface exige refatoração cara depois.
  • Acione a Sally com UH para avaliar os fluxos contra a arquitetura proposta
  • Output: lista de incompatibilidades entre UX e arquitetura, resolvidas antes do desenvolvimento
Fase 4
Desenvolvimento — junto com o Developer
A Sally gera as especificações de interface (US) e os documentos de handoff (UD) que o Developer usa como input para cada story de frontend.
  • Acione a Sally com US antes de cada story de UI
  • Acione com UD para o handoff formal antes do DS do Developer
04UX na fase de descoberta — UX Brief

O UX Brief é o primeiro artefato da Sally e o que mais influencia o produto final. Ele traduz o Project Brief do Analyst em objetivos de experiência concretos — definindo quem é o usuário, o que ele tenta fazer e quais são as restrições de interface que o produto deve respeitar.

O que o UX Brief contém
  • Personas — perfis do usuário primário e secundário com contexto de uso real
  • Jobs to be done — o que o usuário está tentando realizar, não apenas o que o produto faz
  • Princípios de experiência — os valores de design que devem guiar todas as decisões de interface
  • Restrições de interface — dispositivos, contexto de uso, acessibilidade, idioma
  • Métricas de UX — como vamos saber que a experiência é boa? (task completion rate, erro rate, NPS)
  • Referências — produtos com experiências que inspiram ou que devemos evitar
Como usar o UX Brief: passe o UX Brief para o PM antes de criar o PRD. O PM vai usar os Jobs to be Done como base para as user stories e os princípios de experiência como critério de aceite implícito para todas as features.
05UX na fase de planejamento — User Flows

Os user flows são o artefato de UX mais valioso para o PM e o QA. Eles revelam lacunas no PRD que critérios de aceite textuais não capturam — especialmente estados de erro, fluxos alternativos e transições entre telas.

O que passar como contexto para o trigger UF
  • O PRD — a Sally analisa cada requisito funcional e cria o fluxo correspondente
  • O UX Brief — garante que os fluxos seguem os princípios de experiência definidos
  • As restrições técnicas relevantes — o que é possível de implementar dado o modelo de dados e a arquitetura
O que um bom user flow documenta
  • Happy path — o fluxo ideal quando tudo funciona
  • Caminhos alternativos — usuário que pula etapas, volta, cancela
  • Estados de erro — o que acontece quando algo falha e como o usuário se recupera
  • Estados vazios — o que o usuário vê antes de ter dados (first-time experience)
  • Estados de carregamento — feedback durante operações assíncronas
  • Pontos de decisão — onde o sistema ou o usuário toma uma decisão que bifurca o fluxo
Dica: após gerar os user flows com UF, leve-os de volta ao PM. Frequentemente os fluxos revelam requisitos que o PRD não cobriu — estados de erro, permissões de acesso ou fluxos de onboarding que parecem óbvios no texto mas são complexos na prática.
06UX na fase de arquitetura

A fase de arquitetura é onde UX e tecnologia precisam conversar — e onde a maioria dos times não faz isso. Decisões de modelo de dados e API que parecem neutras tecnicamente podem impossibilitar estados de interface importantes ou forçar roundtrips desnecessários que degradam a experiência.

Perguntas que o UX Designer deve fazer ao Architect
  • O modelo de dados suporta paginação sem recarregar a página inteira?
  • A API retorna dados suficientes para renderizar o estado otimista sem esperar confirmação do servidor?
  • Como o sistema lida com operações offline ou com conectividade intermitente?
  • Há endpoints que suportam busca e filtro em tempo real sem latência perceptível?
  • O modelo de permissões suporta os diferentes níveis de acesso mapeados nos user flows?
Use UH para validar arquitetura × UX

O trigger UH (UX Heuristics) pode ser usado nesta fase para avaliar os user flows contra a arquitetura proposta. A Sally identifica pontos de fricção que surgiriam da implementação da arquitetura — antes de uma linha de código ser escrita.

07UX na fase de desenvolvimento

Durante o desenvolvimento, a Sally gera dois tipos de artefato: as especificações de interface (US) que detalham como cada tela e componente deve se comportar, e os documentos de handoff (UD) que o Developer usa como input direto para implementar uma feature.

UX Spec (US) — por componente ou tela
  • Comportamento de cada elemento interativo (hover, focus, active, disabled)
  • Regras de validação de formulários com mensagens de erro específicas
  • Lógica condicional de visibilidade de componentes
  • Comportamento responsivo — o que muda entre mobile e desktop
  • Requisitos de acessibilidade — ARIA labels, ordem de tab, contraste mínimo
  • Animações e transições — duração, easing, gatilho
UX Handoff (UD) — por feature completa

O handoff é gerado para features maiores que envolvem múltiplas telas ou componentes. Ele consolida todos os specs em um único documento estruturado que o Developer usa como input para o trigger DS.

Sally: UD
→
Developer: DS
→
Developer: CR
→
Sally: UH review
08UX → PM — enriquecendo o PRD

Os artefatos de UX alimentam o PM em dois momentos principais:

HANDOFFS: Sally → John (PM)
UX Brief
→
PM usa as Personas e Jobs to be Done para escrever user stories mais centradas no usuário real
User Flows
→
PM usa os fluxos para identificar requisitos ausentes no PRD e refinar critérios de aceite com estados específicos
UX Heuristics
→
PM usa os problemas de usabilidade identificados como backlog de melhorias priorizáveis
Regra prática: todo critério de aceite de uma story de UI deve ter um correspondente no user flow ou no UX spec. Se o Dev não sabe qual mensagem de erro mostrar quando a validação falha, o critério de aceite está incompleto.
09UX → Dev — contratos de interface

O handoff de UX para o Developer é o ponto mais crítico do processo. Ambiguidade aqui se traduz diretamente em retrabalho.

HANDOFFS: Sally → Amelia (Developer)
UX Spec
→
Developer usa como input para o DS — especialmente os estados de componente, regras de validação e requisitos de acessibilidade
UX Handoff
→
Developer usa como referência durante toda a implementação de uma feature — substitui perguntas ao designer durante o sprint
User Flows
→
Developer usa para entender o contexto de navegação — para onde o usuário vai antes e depois de cada tela
O que um handoff completo deve especificar
  • Todos os estados possíveis de cada componente interativo (não apenas o estado padrão)
  • Mensagens de erro exatas — não "mostrar erro", mas o texto específico de cada mensagem
  • Comportamento durante carregamento — skeleton, spinner ou progressive disclosure
  • Limites de caracteres em campos de texto e o que acontece quando são atingidos
  • Comportamento em telas pequenas — o que colapsa, o que some, o que muda de posição
  • Requisitos de acessibilidade específicos — não apenas "deve ser acessível"
10UX → QA — critérios de aceite visuais

O QA usa os artefatos de UX para definir o que testar além da funcionalidade — verificando se a experiência implementada corresponde ao que foi projetado.

HANDOFFS: Sally → QA
User Flows
→
QA usa como base para os cenários de teste E2E — cada nó do fluxo é um cenário a ser testado
UX Spec
→
QA usa para testar estados específicos de componente — validação de erro, estados desabilitados, comportamento responsivo
UX Heuristics
→
QA incorpora problemas de usabilidade identificados como casos de teste de regressão de experiência
Dica para QA: o user flow é o mapa dos cenários de teste E2E. Cada caminho no fluxo — happy path, alternativo e de erro — é um cenário. Se o QA não tem um user flow para referência, está testando às cegas.
11Artefatos UX no BMAD — onde vivem

Todos os artefatos de UX devem ser versionados no repositório junto com o código — não em ferramentas externas isoladas.

Estrutura recomendada em docs/
docs/
└── ux/
    ├── ux-brief.md              ← UB — princípios e personas
    ├── user-flows/
    │   ├── flow-auth.md         ← UF por feature
    │   ├── flow-checkout.md
    │   └── flow-onboarding.md
    ├── specs/
    │   ├── spec-login-form.md   ← US por componente
    │   └── spec-dashboard.md
    ├── handoffs/
    │   └── handoff-checkout.md  ← UD por feature
    └── audits/
        └── audit-v1.md          ← UA histórico

Com os artefatos no repositório, o Developer pode referenciar o spec diretamente no contexto do Claude Code ao usar o trigger DS — sem precisar sair da ferramenta para consultar o design em outro sistema.

12Erros comuns e como evitar
❌
UX entrando somente após o PRD aprovado — o custo de mudar um fluxo depois que o PM validou o PRD é 3x maior do que co-criar o PRD com UX desde o início. Insira a Sally na fase de brainstorming.
❌
Handoff sem estados de erro documentados — "mostrar mensagem de erro" não é uma spec. O Developer precisa saber exatamente qual texto mostrar, quando mostrar, e como o usuário se recupera do erro.
❌
User flows sem caminhos alternativos — um flow que só documenta o happy path é metade de um flow. Os caminhos de erro e recuperação são onde a experiência real é vivida.
⚠
Não validar UX contra arquitetura — um fluxo que requer 5 chamadas de API para renderizar uma tela vai ser lento em produção. A conversa entre UX e Architect antes do desenvolvimento evita esse problema.
⚠
Artefatos de UX fora do repositório — specs em Figma, flows em Miro e critérios no Notion criam fragmentação de contexto. O Developer não vai abrir três ferramentas para implementar uma story. Centralize em docs/ux/.
